# Sprint 3 — Brief, Moodboard y Portal de Clientes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** El CLIENT de un proyecto ACTIVE completa su brief (cuestionario + archivos de referencia) y reacciona/comenta las piezas del moodboard que carga el equipo, con aislamiento estricto por `project_id` y UI mobile-first Tactile Brutalism.

**Architecture:** Tres tablas nuevas (`brief_items`, `moodboard_items`, `moodboard_reactions`) + migración Alembic `0004`. Endpoints FastAPI bajo `/api/v1/projects/{project_id}/brief|moodboard` con guards de membresía/rol reutilizando `deps.py`. Archivos en disco local (`MEDIA_ROOT`) servidos solo por endpoints autenticados (S3/R2 queda para un sprint futuro; los settings `STORAGE_*` no se tocan). Frontend Next.js App Router: nuevo portal `/portal/*` para CLIENT y páginas de gestión `/admin/projects/[id]/*` para el equipo.

**Tech Stack:** FastAPI + SQLAlchemy 2.0 async + Pydantic v2 + Alembic (PostgreSQL prod / SQLite in-memory tests), Next.js 14 + TypeScript strict + Tailwind.

**Spec:** `AGENTS.md` (dominio, RBAC, UI) + `docs/architecture.md` §3, §4, §6, §7 + requerimiento Sprint 3 del usuario (brief_items, moodboard_items con LIKE/DISLIKE/COMMENT, aislamiento por proyecto, pytest). Contexto exhaustivo del codebase: `docs/superpowers/plans/sprint3-codebase-context.md`.

## Global Constraints

- Comando de tests autoritativo (desde la raíz del repo): `backend/.venv/bin/python -m pytest tests/backend -v`. Baseline: **143 passed**. Ningún test existente puede romperse.
- Gate frontend: `cd frontend && npx tsc --noEmit && npm run build` (strict mode, sin `any` implícitos).
- Modelos: patrón exacto del codebase — UUID PK `Uuid(as_uuid=True), default=uuid.uuid4`; timestamps `DateTime(timezone=True), default=lambda: datetime.now(timezone.utc)` (+`onupdate` en `updated_at`); sin `relationship()`; enums `class X(str, enum.Enum)` persistidos con `SAEnum(X, name="<snake>", native_enum=False, values_callable=lambda members: [m.value for m in members])` (valores lowercase en DB, precedente `MeetingStatus`).
- Migración: `backend/alembic/versions/0004_sprint3_brief_moodboard.py`, `revision="0004"`, `down_revision="0003"`, tipos genéricos SQLAlchemy, enums `native_enum=False`. Tests usan `Base.metadata.create_all`, nunca Alembic.
- Seguridad (AGENTS.md §3): todo endpoint protegido valida autenticación, `is_active == True`, rol permitido y membresía sobre `project_id`. 401 `"Could not validate credentials"`, 403 `"Inactive user"` / `"Insufficient permissions"` / `"No access to this project"` (strings exactos de `deps.py`).
- Aislamiento: toda consulta de ítems filtra `id == item_id AND project_id == project_id del path`. Un ítem de otro proyecto responde **404**, nunca 403 con fuga de existencia.
- Escrituras de brief/moodboard exigen `project.status == ProjectStatus.ACTIVE`; si no, **409 `"Project is not active"`**. Lecturas: cualquier miembro (cualquier status).
- COLLABORATOR: solo escribe si existe `ProjectMember(project_id, user_id, assigned_role=ProjectRole.COLLABORATOR)`. LEAD_DESIGNER: membresía `assigned_role=LEAD_DESIGNER` o `project.lead_designer_id == user.id`. SUPER_ADMIN: bypass. CLIENT: solo acciones de cliente con membresía `assigned_role=CLIENT`.
- Uploads: máximo **10 MiB (10485760 bytes)** → 413 `"File exceeds the 10 MiB limit"`. Tipos brief: `image/jpeg, image/png, image/webp, image/gif, application/pdf`; moodboard: solo las 4 imágenes. Tipo no permitido → 422 `"Unsupported file type"`. El nombre de archivo del cliente NUNCA se usa para construir rutas; la extensión la deriva el servidor del content-type. Binarios fuera de la DB; descarga solo autenticada (sin `StaticFiles` mount público).
- Auditoría (`log_audit`, commitea internamente): acciones `brief.question_create`, `brief.answer`, `brief.reference_upload`, `moodboard.item_create`, `moodboard.item_delete`, `moodboard.reaction`, `moodboard.reaction_delete`; `entity_type` `"brief_item"` / `"moodboard_item"` / `"moodboard_reaction"`; `metadata` incluye `project_id` como str.
- UI (AGENTS.md §4): fondo `#F7F7F5`, tinta `#111111`, superficie `#EFECE6`; `border-radius: 0`, sin sombras/degradados; `grid-brutal` (gap 1px), `label-mono` (11px uppercase mono), `btn-brutal` con `↗`; áreas táctiles **≥ 44×44px** (`min-h-[44px]` y `min-w-[44px]` en botones de reacción); mobile-first 375px, grids colapsan a `1fr`; nada dependiente de `hover`; copy de UI en español, código/docs en inglés.
- Dominio: solo diseño/dirección creativa/documentación/FF&E. Nada de obra, montaje, inventario ni compras.
- Pydantic v2: reads `ConfigDict(from_attributes=True)`, writes `ConfigDict(extra="forbid")`, validators v2.
- Cada tarea termina con commit(s) en la rama `sprint3/brief-moodboard` y la suite completa verde.

## Review Focus

1. **Sustitución de item-id entre proyectos:** miembro válido de A usa el id de un ítem de B bajo el path de A → debe dar 404 (tests en Tasks 3 y 4, `test_project_isolation.py`).
2. **Path traversal en storage:** `storage_key` con `..` o ruta absoluta, o filename malicioso del cliente → `resolve()` rechaza; la extensión sale del content-type, no del filename (Task 2).
3. **Kill switch con token válido:** usuario desactivado después de emitir el token → 403 `"Inactive user"` en todos los endpoints nuevos (Tasks 3 y 4).
4. **Upsert de reacciones:** segundo POST del mismo cliente reemplaza (no duplica) su reacción; LIKE→COMMENT sin texto → 422; constraint único `(moodboard_item_id, user_id)` (Task 4).
5. **Proyecto no-ACTIVE:** escrituras en DRAFT/ON_HOLD → 409; lecturas siguen permitidas para miembros (Tasks 3 y 4).
6. **MIME declarado vs real:** el whitelist usa el content-type declarado por el cliente; sniffing de magic bytes queda fuera de alcance (Ruling en ledger). Lo que sí se valida: tamaño real de los bytes leídos y extensión derivada del tipo (Tasks 2–4).
