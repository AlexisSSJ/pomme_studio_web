# Sprint 5 — Borradores, FF&E y Liberación por Pago Final — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Flujo de borrador interno vs. publicación a cliente de entregables, catálogo de especificaciones FF&E, y liberación de la descarga final condicionada a `balance_paid` con marca de agua y auditoría.

**Architecture:** FastAPI async + SQLAlchemy 2.0 sobre el patrón de Sprint 4 (endpoints delgados, guards en `api/deps.py`, auditoría vía `services/audit.log_audit`, storage local autenticado). Se añaden columnas de visibilidad/handover a `deliverables` y una tabla nueva `project_specifications` (migración `0006`). La marca de agua se genera en servidor con Pillow. `balance_paid` se desacopla de la activación y pasa a ser la liquidación final validada por `SUPER_ADMIN`. Frontend Next.js 14 App Router ("use client", `apiFetch`/`apiFetchBlobUrl`, Tactile Brutalism): gestión admin de visibilidad + validar pago final, catálogo FF&E admin (CRUD), y portal cliente con preview/marca de agua + candado de descarga y catálogo FF&E de lectura.

**Tech Stack:** Python 3.12+ (3.14 local) / FastAPI / SQLAlchemy async / Alembic / Pydantic 2 / Pillow / pytest + pytest-asyncio (SQLite in-memory). Frontend: Next.js 14 + TypeScript strict + Tailwind (verificación `npm ci && npm run build`, sin ESLint ni test runner).

**Spec:** `docs/superpowers/plans/2026-11-21-sprint5-brief.md` (requerimientos + diseño acordado, alcance UI+backend) + `docs/superpowers/plans/sprint5-frontend-context.md` (patrones exactos del frontend) + `AGENTS.md` + `docs/architecture.md`.

## Review Focus

1. **Descarga final antes del pago por URL directa:** un `CLIENT` que llama `GET …/deliverables/{id}/file` sobre un entregable `is_final_handover=True` con `balance_paid=False` debe recibir **403**, no el archivo (el gate es de servidor, no de UI). Test en Task 5.
2. **Colaborador publica o marca handover:** `COLLABORATOR` llamando `publish`/`final-handover` → **403**; además su upload siempre queda `is_client_visible=False` aunque envíe `True` en el form. Tests en Task 4.
3. **Cliente lee un borrador interno:** `GET` detalle/`/file`/`/preview`/`/comments` de un entregable no visible para el `CLIENT` → **404** (sin fuga de existencia); el listado de etapa del cliente filtra los no visibles. Tests en Task 4.
4. **Fuga cross-project:** id de deliverable o specification de otro proyecto bajo el path de A → **404** en todos los endpoints nuevos. Tests en Tasks 4 y 6.
5. **Cambio de `balance_paid` sin auditoría o por rol indebido:** solo `SUPER_ADMIN` valida el pago final; cada cambio exitoso deja `audit_logs` con actor y `project_id`; no-`SUPER_ADMIN` → 403. Tests en Task 2.
