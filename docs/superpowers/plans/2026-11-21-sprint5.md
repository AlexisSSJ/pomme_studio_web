# Sprint 5 — Borradores, FF&E y Liberación por Pago Final — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Flujo de borrador interno vs. publicación a cliente de entregables, catálogo de especificaciones FF&E, y liberación de la descarga final condicionada a `balance_paid` con marca de agua y auditoría.

**Architecture:** FastAPI async + SQLAlchemy 2.0 sobre el patrón de Sprint 4 (endpoints delgados, guards en `api/deps.py`, auditoría vía `services/audit.log_audit`, storage local autenticado). Se añaden columnas de visibilidad/handover a `deliverables` y una tabla nueva `project_specifications` (migración `0006`). La marca de agua se genera en servidor con Pillow. `balance_paid` se desacopla de la activación y pasa a ser la liquidación final validada por `SUPER_ADMIN`.

**Tech Stack:** Python 3.12+ (3.14 local) / FastAPI / SQLAlchemy async / Alembic / Pydantic 2 / Pillow / pytest + pytest-asyncio (SQLite in-memory). Solo backend; sin frontend este sprint.

**Spec:** `docs/superpowers/plans/2026-11-21-sprint5-brief.md` (requerimientos + diseño acordado) + `AGENTS.md` + `docs/architecture.md`.

## Global Constraints

- Comando de tests autoritativo (desde la raíz del worktree): `backend/.venv/bin/python -m pytest tests/backend -q`. Baseline: **299 passed**. Ningún test existente puede quedar roto al final (los de Sprint 4 afectados por el gate de visibilidad se actualizan en Task 4, sin debilitar assertions).
- Roles válidos: `SUPER_ADMIN`, `LEAD_DESIGNER`, `COLLABORATOR`, `CLIENT`. Todo endpoint protegido valida en orden: autenticación (401 `"Could not validate credentials"`), `is_active` (403 `"Inactive user"`), rol (403 `"Insufficient permissions"`), membresía (403 `"No access to this project"`). Strings exactos de `deps.py`.
- Escrituras de proyecto exigen `project.status == ACTIVE`; si no → 409 `"Project is not active"` (helper `require_active_project`). Lecturas: cualquier miembro, cualquier status.
- Aislamiento por ítem: toda consulta de recurso anidado filtra `id == resource_id AND project_id == path project_id`; id de otro proyecto → 404 (sin fuga de existencia).
- Toda tabla nueva requiere migración Alembic (`backend/alembic/versions/0006_sprint5_drafts_ffe_handover.py`, revision `"0006"`, down_revision `"0005"`); prohibido `create_all()` en producción. Tests usan `Base.metadata.create_all`.
- Acciones sensibles → `log_audit(db, actor_user_id=…, action=…, entity_type=…, entity_id=…, metadata={… "project_id": str(project_id) …})`.
- Uploads: 10 MiB → 413 `"File exceeds the 10 MiB limit"`; tipo no permitido → 422 `"Unsupported file type"`; clave `<project_id>/<uuid_hex><ext>` vía `LocalStorage`; descarga solo por endpoint autenticado. Entregables siguen siendo solo imágenes (`MOODBOARD_CONTENT_TYPES`).
- Enums SQLAlchemy: `SAEnum(..., name="<snake>", native_enum=False, values_callable=lambda members: [m.value for m in members])`, valores lowercase, `server_default` lowercase (patrón `DeliverableStatus`).
- Modelos: UUID PK `Uuid(as_uuid=True), default=uuid.uuid4`; timestamps `DateTime(timezone=True), default=lambda: datetime.now(timezone.utc)` (+`onupdate` en `updated_at`); sin `relationship()`.
- Pydantic v2: reads `ConfigDict(from_attributes=True)`; writes `ConfigDict(extra="forbid")`.
- Dominio: solo diseño/dirección creativa/documentación/FF&E. FF&E es documentación de especificación: **sin cantidades, precios, stock, órdenes de compra ni inventario**.
- Commits frecuentes por tarea; mensajes estilo repo (`feat(backend): …`, `test(backend): …`, `fix(backend): …`, `docs: …`).
- Verificación de migración (opcional pero recomendada): `cd backend && .venv/bin/python -m alembic upgrade head` contra una BD SQLite temporal para confirmar que `0006` aplica y revierte.

## Review Focus

1. **Descarga final antes del pago por URL directa:** un `CLIENT` que llama `GET …/deliverables/{id}/file` sobre un entregable `is_final_handover=True` con `balance_paid=False` debe recibir **403**, no el archivo (el gate es de servidor, no de UI). Test en Task 5.
2. **Colaborador publica o marca handover:** `COLLABORATOR` llamando `publish`/`final-handover` → **403**; además su upload siempre queda `is_client_visible=False` aunque envíe `True` en el form. Tests en Task 4.
3. **Cliente lee un borrador interno:** `GET` detalle/`/file`/`/preview`/`/comments` de un entregable no visible para el `CLIENT` → **404** (sin fuga de existencia); el listado de etapa del cliente filtra los no visibles. Tests en Task 4.
4. **Fuga cross-project:** id de deliverable o specification de otro proyecto bajo el path de A → **404** en todos los endpoints nuevos. Tests en Tasks 4 y 6.
5. **Cambio de `balance_paid` sin auditoría o por rol indebido:** solo `SUPER_ADMIN` valida el pago final; cada cambio exitoso deja `audit_logs` con actor y `project_id`; no-`SUPER_ADMIN` → 403. Tests en Task 2.
